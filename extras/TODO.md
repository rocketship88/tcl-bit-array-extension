- [x] DONE 2026-10-18 (0.8.1): `lpop l INDEX` crashed (BASetElement got valueObj == NULL, which the core passes for lpop).  Fixed: with NULL the hook checks the index (error if >= length), makes a COPY of the array, deletes the element from the copy with BAReplace and returns the copy (reference count 0).  Always a copy, even when the value is not shared, on purpose: the core's Tcl_LpopObjCmd calls TclUndoRefCount on whatever the hook returns, as if the hook had added a reference the way TclLsetFlat does, but the hook contract used by TclLsetList (the lset command) is that the core adds it.  A hook that returns its own argument would be left with reference count 0 while a variable holds it.  See DESIGN_LOG.md.  11 tests (lpop-1.1 to 1.11), mutants L01-L04.  Still to do on the core side: nothing from us (see the next entry).
- [ ] (2026-10-18) Core bug (ET filed tickets on 2026-10-18 from the fresh Claude's mutation run; one has a reply saying the analysis was correct; ticket numbers not recorded here, ask ET): Tcl_LpopObjCmd with an index on an abstract list gets the reference count wrong.  Two paths: (a) a type WITHOUT setElementProc (the tcltest `lstring`, which has NULL for SetElement) goes through TclLsetFlat + TclUndoRefCount: `set l [lstring abcd]; lpop l 1; set r [list $l]; set l 5; lappend r x; puts $r` prints `{} x` on trunk 9.1.1 (expected `{a c d} x`); not reproduced with the shipped `lseq` on a delivered 9.1.1 tclsh (checked 2026-10-18; the lreverse list type was not checked); (b) a type WITH setElementProc (bitarray) goes through `proc(...)` + TclUndoRefCount: the hook's result gets a reference removed that nobody added (TclLsetList increments the hook's result itself, Tcl_LpopObjCmd does not).  bitarray 0.8.1 works around (b) by always returning a new object for lpop.  Several of the problems found were segfaults.
