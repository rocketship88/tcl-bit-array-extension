Sections 8-13 are new in 0.3.  Sections 1-7 are the 0.2 results, kept for history; where a number there was for 1-bit

8. Test suite (0.3)
   tests/bitarray.test: Total 134, Passed 134, Failed 0.  Also with -DBA_NO_BUILTINS, with -DBA_FORCE_32BIT_LIMITS, and with
   both.  68 new tests: width option parsing, value ranges and error text for each width, lindex/lset/lrange/lreverse/
   lappend/linsert/lreplace/foreach/lsort/in on wide arrays, copy-on-write, fill/count/next for each width (including
   word-boundary starts for the byte scan and the memchr path), 64-bit extremes, canonical-spelling rules for "in", a
   check that the removed command "from" is gone, and a memory-growth test (mem-1.1, needs /proc).
   New randomized test tests/diff_width.tcl: for width W in 8/16/32/64 (and 1), random lappend / linsert / lreplace /
   lset (including at the end) / lrange / lreverse / fill with step / alias-copy safety / "in" (including non-canonical
   spellings) / lsort / foreach / count and next (with and without a value) against a plain list holding the same values
   (edge values 0, 1, max, max-1, min, min+1 are drawn often).  In the suite: 4 widths x 3 seeds x 60 iterations, plus
   2 seeds at width 1.  By hand: 5 widths x 10 seeds x 100 iterations x 40 steps = 200,000 steps, 0 differences.
   The only legitimate type loss in these runs is the linsert-of-one-element-at-the-end case noted in README.md (explained in section 13a); the test
   expects it and fails on any other loss of the bitarray type or of the width.
   Test bugs found and fixed while writing them: wrong expectations for list-quoting of "<>" and for a string-reversed
   copy (which is a string, not a bitarray), a value generator that could draw 45 for a 1-bit array.  No bug in
   bitarray.c was found by the new tests on the first run; the first full differential run reported only the known
   linsert case (which the test now expects).

9. Memory safety (0.3)
   valgrind --leak-check=full on the whole 134-test suite: 0 invalid reads or writes, 0 uninitialised reads, 0 definitely
   lost, 0 indirectly lost.  valgrind prints 100 "possibly lost" records; they are blocks that Tcl's own allocator is
   still holding at exit (start-up allocations, the byte-code cache, the global test variables).  Two of them are reached
   through bitarray's getElements (an element vector and the integer objects it holds for an array still alive when
   tclsh exited).  I read them as memory still in use at exit, not leaks, for two reasons: they are the same kind as
   the other 98, and the growth test below is flat.
   Memory-growth test (tests/leak_check.tcl, run by mem-1.1): at every width, build 300,000 distinct values, build the
   element cache (lsort), drop it (lset), append, slice, unset; resident size after rounds 2 and 6 differs by less than
   40 MB (typically about 0 MB).  Run with two leaking mutants (the cache's integer objects never released, or the cache
   length not recorded) the same loop grows by about 260 MB per 2 rounds, and the test fails.  16 million lindex calls
   returning values above 1 (new integer objects with reference count 0) leave the resident size unchanged.  Earlier,
   in 0.2: unset after creating a 953 MiB array returns the memory (960 MB -> 6.6 MB RSS); the same for an array held in
   a list or as an array element, and overwriting a variable.

10. Mutation testing, 0.3 (extras/mutate5.py, extras/mutation_round5.txt)
   95 mutants of bitarray.c (the 42 from round 4, updated to the new code, plus 53 aimed at the width code: element
   offsets and widths in GetElem/PutElem, value-range checks, sign handling, allocation sizing, the element cache, slice/
   reverse/move/replace for wide data, string form, "in", count/next/fill for each width, option parsing).
   "Caught" = a test fails or the run crashes.  81 caught, 14 missed.
   The first run had 79 caught, 16 missed; the two extra misses were mutants that leak memory (the cache's integer objects
   never released; the cache length not recorded).  No test can see a leak, so I added the memory-growth test mem-1.1
   (section 9), which catches both.  I made no other test change for this round.
   The 14 misses and my reasons (judgement, not proof):
     M06 M08 M42  checks the core already makes before calling the hook (it clamps the indexes), so unreachable.
     M07 M31 M36 M38  stray bits beyond the end of a 1-bit array (an unmasked slice tail, a fill-with-ones tail, bits not
                  cleared when the array shrinks, spare capacity not zeroed).  Every reader bounds or masks by the
                  length and every newly exposed bit is written first.
     W26          the same for wide arrays: bytes beyond the end are not cleared when an array shrinks; no reader looks there.
     M33 M34 W14  size checks that on a 64-bit build the allocator or the next check makes again; they matter only on 32-bit.
     M35          capacity grows by exactly the words needed instead of doubling; no visible difference at test sizes.
     W08          an equivalent mutant: converting a 64-bit pattern to a signed value gives the same result either way here.
     W24          memcpy instead of memmove for overlapping moves; glibc's memcpy behaves like memmove for these sizes, so no
                  test can see it, but the C standard says it is undefined, so the code keeps memmove.
   Raw output: extras/mutation_round5.txt (and extras/mutation_round5_first_run.txt for the run with 16 misses).

13a. lappend / linsert turning a bitarray into an ordinary list (core behaviour; found 2026-10-13)
   Not specific to bitarray.  Tcl core code appends through two different paths; the one through Tcl_ListObjReplace calls the
   type's Replace hook (the type is kept), the one through Tcl_ListObjAppendElement / TclListObjAppendElements -> TclListObjGetRep ->
   SetListFromAny converts the object to a real list in place.  Which path runs depends on how the command is evaluated:
      linsert $l end X   compiled (INST_LREPLACE -> Tcl_ListObjReplace)               kept
      linsert $l end X   not compiled (Tcl_LinsertObjCmd special case)               LOST
      linsert, 2+ elements or not at the end                                         kept
      lappend v X [Y..]  compiled in a proc (lappendScalar / lappendListDirect)      LOST
      lappend            compiled at global/namespace level (lappendListStk)         kept
      lappend            not compiled (Tcl_LappendObjCmd)                            kept
   lset, lrange, lreverse, lreplace, lindex, llength keep the type in every context tried.
   The earlier "top level loses, loop keeps" impression was this: the main script file given to tclsh is, from reading
   Tcl_FSEvalFileEx, evaluated directly (not compiled), a sourced file and a proc body are compiled.  Not confirmed in a debugger.
   Reproduced with stock Tcl and no extension, using the core's own test type [lstring] (it has a Replace hook; it exists only in the
   tcltest shell): extras/typeloss_lstring_repro.tcl, output in extras/typeloss_lstring_repro_output.txt, run on a clean tcltk/tcl checkout
   e36db3376a2d7d4857f6c766bd6133fc7b29e821 (2026-10-02) and, by the repository owner, on a second Linux machine (stock tree,
   Fossil check-in 4991a47b94705ddff07bd81cab83291e5f6d219a8a75b54a32c954e73b05eaae); identical output.  The same table with
   bitarray: extras/typeloss_bitarray_repro.tcl (output typeloss_bitarray_repro_output.txt) (earlier trunk 3d77be8951).
   tests/abstractlist.test in Tcl checks several [lstring] commands for type loss but, as far as I found, not lappend onto an
   lstring, a single-element linsert at the end, or compiled versus uncompiled.
   Reported to the Tcl core by the repository owner on 2026-10-13: https://core.tcl-lang.org/tcl/tktview/0c82728f85760f36361fe42a15f55453c94d285d
   Not tested: other platforms, Tcl 9.0.x (no version-2 abstract lists), other compilers.  Whether the core team treats it as a bug
   is not known.  The text of the report is extras/typeloss_ticket.md.

5. 32-bit / portability changes (0.1.1)
   Sizes are now range-checked as 64-bit values before being narrowed to Tcl_Size; the limit comes from #if SIZE_MAX
   (2^40 on 64-bit, 2^30-1 on 32-bit); a fill step is clamped before narrowing; the new length in lreplace/linsert/
   lappend is computed in 64-bit arithmetic; the element-vector allocation is overflow-checked.  Bit count and
   count-trailing-zeros use gcc/clang builtins, or plain C elsewhere.
   Checked: suite passes with builtins and with -DBA_NO_BUILTINS; the plain-C functions match the builtins on
   5,000,064 values; the 32-bit limits were exercised on this 64-bit machine with -DBA_FORCE_32BIT_LIMITS
   (2^30-1 ok, 2^30 refused, growth past it refused, a step of 4294967301 handled).
   NOT checked: an actual 32-bit compile or run (-m32 headers are not installed here); Windows/MSVC.
   Mutation testing (extras/mutation_round3.txt): 34 mutants, 28 caught, 6 missed.  The two new misses, M33 and M34,
   remove the new range checks in "bitarray new" and in lreplace/linsert; on a 64-bit build they are redundant with
   the check inside the allocator, so they can only matter on a 32-bit build, which I could not run.
